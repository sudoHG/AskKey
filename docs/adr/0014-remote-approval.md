# ADR 0014: Remote approval from a paired iPhone

## Status

Accepted. Stage 4 of the multi-device roadmap in [#269](https://github.com/sudoHG/AskKey/issues/269); the specification is [#308](https://github.com/sudoHG/AskKey/issues/308), and [#309](https://github.com/sudoHG/AskKey/issues/309) records it here. [#310](https://github.com/sudoHG/AskKey/issues/310) adds the message kinds to `AskKeyDevices`, [#311](https://github.com/sudoHG/AskKey/issues/311) the Broker and Vault paths, [#312](https://github.com/sudoHG/AskKey/issues/312) the Mac coordinator, [#313](https://github.com/sudoHG/AskKey/issues/313) the Mac interface, [#314](https://github.com/sudoHG/AskKey/issues/314) the iPhone approver, [#315](https://github.com/sudoHG/AskKey/issues/315) the notification extension, [#317](https://github.com/sudoHG/AskKey/issues/317) and [#318](https://github.com/sudoHG/AskKey/issues/318) the Release build and distribution; [#316](https://github.com/sudoHG/AskKey/issues/316), [#319](https://github.com/sudoHG/AskKey/issues/319) and [#320](https://github.com/sudoHG/AskKey/issues/320) are the maintainer's real-device checks.

This ADR amends [ADR 0002](0002-broker-and-approval-protocol.md), [ADR 0006](0006-release-process.md), [ADR 0008](0008-approval-shows-target.md), [ADR 0011](0011-in-app-updates.md) and [ADR 0013](0013-device-identity-and-pairing.md); each has a short amendment section that points here. The Broker protocol and its version do not change, and agents cannot see devices or choose where a request is decided.

## Context

An agent's Ask request can only be decided at the Mac that runs the agent, and only while its screen is unlocked. Someone who starts a long agent task and walks away comes back to a failed task. Stage 2 gave the Mac and the iPhone a verified pairing and an end-to-end encrypted channel through the account's private CloudKit database (ADR 0013), but nothing uses it yet.

The maintainer decided on 2026-11-14:

1. **What the iPhone approves.** Read requests only: Deny, Allow Once, and the single-credential timed allowance. When End Timed Allow on Lock is on, the iPhone never offers the timed allowance, whether the Mac is locked or not; when it is off, the iPhone may offer it even while the Mac is locked. Writes, organize operations and group allowances stay on the Mac.
2. **When a request reaches the iPhone.** At once while the Mac is locked or its lock state is unknown; otherwise after 20 seconds without a decision, or at once if the Mac locks during the wait.
3. **Turning approval on.** Per iPhone on the Mac, off by default, system authentication on the Mac plus a six-digit approver code typed on that iPhone with Face ID; it covers every Ask credential.
4. **Face ID.** Allow needs Face ID and an approval-key signature. Deny needs no Face ID; it is still authenticated with the message key and the same bindings, can never grant anything, and is padded to the Allow length. Accepted side effect: someone holding the unlocked phone can deny.
5. **Notification.** The notification shows the request in the v0.2 card sentence (requester, Mac, credential and the program's name), never a credential value, and only after the notification extension fetched, decrypted and verified a request from a Mac the iPhone approves for; otherwise generic text. The details come from the decrypted record, never from the push. Show Previews controls the lock screen, and details stay in Notification Center. The time-sensitive budget stays.
6. **Distribution.** A public TestFlight link first. The App Store follows once the TestFlight build is stable, as a separate issue after #320.
7. **Notification filtering entitlement.** Not requested in this stage.
8. **#304.** After stage 4. Stage 4 adds only the install reminder and the fixed download link.

This ADR records those decisions as decided and fixes what #308 left open. Where it resolves an ambiguity in #308 or departs from its wording, it says so under [Resolutions of #308](#resolutions-of-308).

## Decision

### What the iPhone decides

- The iPhone decides **read approvals** only: the requests the Broker creates for runtime delivery to a command (`BrokerApprovalOperation.read`, one request per Ask credential in a run). It is offered **Deny**, **Allow Once** and, under the rule below, the **timed allowance for that one credential**.
- **Timed allowance.** While End Timed Allow on Lock is on, the iPhone is never offered the timed allowance, whether the Mac is locked or not, and the Broker's remote path refuses it. While it is off and timed allowances are on, the iPhone is offered the timed allowance, including while the Mac is locked. Locally a timed allowance can only start while the screen is unlocked, because the Mac's prompt only works then; from the iPhone it can now start while the Mac is locked and nobody is at it. It is an ordinary timed allowance (ADR 0002): global for the local macOS user, so any program running as that user can use the credential for its duration, which the Mac's setting caps.
- Writes (create, modify, delete), organize operations and the group timed allowance are never sent to the iPhone. A write card can reveal frozen values on the Mac with system authentication, which the iPhone must never receive, and a group allowance's snapshot is withdrawn whenever a member changes. The decision codes leave room for a group allowance later; writes are excluded by this ADR, not by the code space.
- A request whose display the Mac had to shorten to fit a field's cap, or whose delivery metadata is unavailable (the card's "this run will be refused" case, ADR 0008), is sent with Deny as the only offer.
- A remote Allow always needs Face ID or Touch ID on the iPhone, also when the Mac's read approval authentication is turned off.

### Approvers

- A paired iPhone becomes an **approver** only through **Approve agent requests** on its row in Settings → Devices on the Mac. It is off for every device, including after pairing again, and covers every Ask credential; there is no per-credential setting.
- **Turning it on** widens authority and takes three steps:
  1. On the Mac, in the management session, the person turns it on and passes system authentication. The sheet shows the device's name, platform (self-declared), paired date and last delivery check, says what will leave the Mac (the agent's name, the credential's name, the command and folder and the delivered names, encrypted to that iPhone; never a value), and shows the **approver code**: six digits drawn uniformly from 000000–999999 with the system's random number generator, written `123 456`. The code is never sent, logged, put in a notification, a test identifier or an accessibility label or value.
  2. On the iPhone, the person opens that Mac in Paired Macs, chooses **Approve Requests from This Mac**, types the code into a plain numeric field (not a one-time-code field) and passes Face ID, which the approval-key signature asks for. The screen names the Mac by the iPhone's own name for it and says the code appears only on the Mac's screen. The iPhone removes white space, sends nothing unless exactly six ASCII digits remain, then sends an approver confirmation (kind 14) and, once CloudKit has saved it, sets its own approval flag for that Mac. It cannot learn whether the Mac accepted.
  3. The Mac turns approval on only when a confirmation from the entry the person selected carries the code proof for the code it is showing. A verified confirmation from that entry with a different proof counts as one wrong code; the third ends the attempt. A confirmation from any other entry whose proof matches the code ends the attempt too, and the sheet says the code was entered on a different device than the one selected; one that does not match is refused without counting.
- The code exists only while the sheet is open, for at most 5 minutes. Closing the sheet, locking management, the expiry, the third wrong code, a match from another device, or success discards it; starting again repeats step 1, system authentication included. Until then the open sheet keeps the management session from expiring for idleness, as the pairing sheet does.
- A confirmation re-inserted from an earlier attempt, within its 10-minute lifetime, matches only if the new code happens to equal the old one (about 1 in 1,000,000), and then it can only enable the device the person selected, which signed that confirmation for this Mac with Face ID; otherwise it can only use up attempts, which costs availability, not trust. Someone who never saw the code guesses right with a probability of about 3 in 1,000,000 each time the sheet opens.
- This closes ADR 0013's leftover route by which a device paired through the residual pairing attack became an approver: the impostor never sees the code. It does not attest that the phone runs the genuine app or protects its key as ADR 0013 requires; nothing can.
- **Turning it off** reduces authority and needs the management session only. On the iPhone, **Stop Approving for This Mac** clears the iPhone's own flag, after which it refuses that Mac's requests; the Mac's setting is changed on the Mac.
- **Storage.** Each paired-device list entry gains an approval flag. On the Mac it means "this iPhone may decide my requests", on the iPhone "I accept requests from this Mac". The entry disappears on removal, and a device that pairs again gets a new entry with the flag off. The list serialization becomes version 2: the JSON entry gains the Boolean key `approver`, which version 2 requires; version 1 lists decode with every flag off, and every write produces version 2. The Mac's list keeps its HMAC label and key (ADR 0013). On the Mac the Vault treats a flag change from off to on like adding a device: the write needs the management session and an **approver authorization** for that device ID and pairing ID, which the App holds only after step 1's system authentication and a verified, matching confirmation, and which the write uses up. A change from on to off needs the management session. On the iPhone only the app writes the list. The agent access policy item is not used, so its merge, recovery and delivery-comparison rules do not change.
- **Active-approver set.** The Broker keeps an in-memory set of active approvers: for each, its pairing ID as an opaque 16-byte value (`AskKeyBroker` does not depend on `AskKeyDevices`) and an **enablement generation**, a number the Broker assigns from a counter that only grows. It also keeps a **revocation counter**, which every removal from the set and every emptying of it increments. To add approvers, either when the device services become ready or after a flag write commits, the App reads the revocation counter, then reads the list, then asks the Broker to add the entries whose flag is on, passing the counter it read; the Broker refuses the whole addition if the counter has changed, and the App starts again. Every added entry gets a new generation, so turning approval off and on again, or reloading the set, never revives an earlier generation. Every path that ends or suspends a device's authority first removes it from the set under the Broker's approval lock, and only then writes storage or closes requests (see [Revocation](#revocation-removal-and-account-changes)). When it seals a request, the App records the approver's current generation in the outstanding entry, and the Broker's remote path requires the pairing ID to be in the set with that generation, inside the same locked transition from pending. A revocation that has returned therefore wins over every decision not yet applied, including one for a request sealed before approval was turned off and on again. The set is the linearization point.

### When a request goes to an approver

- A read request is **eligible** when it is pending with a display summary, at least one approver is in the active set, the device services are ready, the iCloud account is available, and agent access is not paused. The coordinator checks this when the Broker creates the request, at the 20-second mark and when the screen locks during the wait; a request that is not eligible at those moments stays on the Mac.
- If the Mac's screen is locked or its state is unknown when the request is created, the Mac sends it to every approver at once. If the screen is unlocked, the Mac's prompt appears as today and the request goes to the approvers only if it is still pending **20 seconds** after it was created, or at once if the screen locks first. The delayed send re-reads the request's status on the coordinator's actor just before sealing; a request decided on the Mac within those 20 seconds never leaves the Mac.
- At most **16** requests are outstanding per approver; further ones stay on the Mac for that approver. A replacement request (see [Applying](#verifying-and-applying-a-decision)) takes its predecessor's place.
- The Mac never seals a request whose deadline has passed.
- From the moment a request is eligible until it is decided, closed or expires, the Mac holds a process activity with the options `ProcessInfo.ActivityOptions.userInitiated`, which prevents App Nap and idle system sleep, and ends it when no request needs it. A closed lid or a manual sleep still sleeps.
- The Mac's own prompt keeps its current behavior, including hiding details while the screen is locked.

### Encodings

The rules of ADR 0013 → Encodings apply: domain labels are ASCII followed by one NUL byte, integers and times are big-endian, times are 8-byte Unix seconds, IDs inside binary structures are 16 raw bytes, and every variable-length field is a 4-byte length followed by its bytes. A text field is UTF-8. Every payload of kinds 10–14 starts with the **pairing ID** (16) and a **layout version** (1 byte, `1`). The recipient refuses a payload with another layout version, a reserved value, a field over its cap, a field that is not valid UTF-8, or trailing bytes, as malformed; a new layout needs a new layout version and its own ADR change. All five kinds use base-mode HPKE, have a maximum lifetime of 10 minutes, and are refused unless the pairing ID matches the sender's current entry on the recipient's list.

**Binding digest** (32 bytes): SHA-256 over `AskKey approval binding v1` followed by eight length-prefixed UTF-8 strings, in this order: the Broker request ID, the operation ID, the credential ID, the target ID, the operation's raw value (`read`), the payload digest, the read projection digest, and the retransmission digest. The strings are exactly those the Broker holds, with no case folding or normalization (the Broker accepts hexadecimal digests in either case and compares them as strings). An absent optional digest is the empty string, which the Broker never accepts as a present value. Every string is at most 4 KiB (`BrokerLimits.maximumFieldBytes`). The Mac keeps the raw values in its outstanding entry; the iPhone cannot check the digest and does not need to.

**Approval request (kind 10).** Field order and caps:

| # | Field | Bytes | Rule |
|---|---|---|---|
| 1 | Pairing ID | 16 | |
| 2 | Layout version | 1 | `1` |
| 3 | Response ID | 16 | random, new for every sealed request; never derived from anything else |
| 4 | Binding digest | 32 | |
| 5 | Request deadline | 8 | the Broker request's expiry on the Mac's clock, rounded down to the second; later than the inner message's sent time and at most 300 seconds after it |
| 6 | Launch time | 8 | when the Mac App process started |
| 7 | Offers | 1 | bit *n* set means decision code *n* is offered; exactly `0x01` (Deny only), `0x03` (Deny, Allow Once) or `0x07` (also the timed allowance) |
| 8 | Timed duration | 8 | the Mac's current timed allowance setting in seconds, 1–7,200 (the Broker's maximum), when bit 2 of the offers is set; otherwise 0 |
| 9 | Display flags | 1 | bit 0: delivery metadata unavailable; other bits 0 |
| 10 | Shortened flags | 1 | bit *k* set means field 11 + *k* was shortened (bit 6: a delivery row was shortened or dropped); bit 7 is 0 |
| 11 | Requester name | 4 + ≤ 256 | the Broker's sanitized caller name; empty when absent, and the iPhone then shows its own "Local Agent" |
| 12 | Purpose | 4 + ≤ 1,024 | may be empty |
| 13 | Credential name | 4 + ≤ 1,024 | the trusted name the Mac card shows; not empty |
| 14 | Command line | 4 + ≤ 6,144 | as the card renders it (ADR 0008); not empty |
| 15 | Working directory | 4 + ≤ 1,024 | home abbreviated; empty when absent |
| 16 | Executable name | 4 + ≤ 256 | the card's last path component, which the Vault already abbreviates to 64 characters; not empty |
| 17 | Delivery row count | 1 | 0–64; 0 when display flag bit 0 is set |
| 18 | Delivery rows | ≤ 3,072 in all | each row: kind (1 byte: 1 environment variable, 2 temporary file) ‖ label (4 + ≤ 256; the component's name for a bundle; empty for a single-material credential, and the iPhone then shows field 13) ‖ variable (4 + ≤ 256, not empty) |

- The fields are built from the same App-derived data as the Mac card (ADR 0008): the display summary's command line, working directory and executable name, which the Vault has already shell-quoted and escaped, and the delivery rows the card's "Hands over" lists: for a bundle, one row per delivered component in the metadata's order; otherwise the environment-variable rows, then the temporary-file rows. A read request without a display summary is never sent. Every text field is **preformatted plain text**: the Mac sends what its card shows, and the iPhone never quotes or escapes it again. The Broker and Vault keep Cc and Cf characters out of fields 11–13 but not line or paragraph separators, so before encoding the Mac replaces every scalar in fields 11–13 that belongs to Foundation's `CharacterSet.controlCharacters` or `CharacterSet.newlines` with `\x` escapes of its UTF-8 bytes, as the Vault does for the other fields (backslashes are left as they are). The iPhone refuses, as malformed, a request with such a scalar in any text field. The Vault's 64-character abbreviation of the executable name and the 160-character command summary are part of the card on both devices and are not shortening in the sense below.
- **Shortening.** A text over its cap becomes *P* ‖ `…` (U+2026, 3 bytes) ‖ *S*, where *P* is the longest prefix of whole Unicode scalars of at most ⌈(cap − 3) / 2⌉ bytes and *S* the longest suffix of whole scalars that fits the rest of the cap. Delivery rows are built in order with each label and variable shortened to its cap, and are kept while the rows' total stays within 3,072 bytes; the first row that does not fit and every later row are dropped. Any shortened field or dropped row sets its flag, and any set shortened flag, or display flag bit 0, makes the offers `0x01`. The iPhone refuses a request that breaks this rule.
- **Size.** The fixed fields take 92 bytes; with every field at its cap the payload is 12,917 bytes, 3,467 below the 16 KiB inner-message cap (`InnerMessage.maximumPayloadByteCount`), which does not change. Sealing a larger payload fails in `InnerMessage.make`.
- **Never in a request:** the request's capability, any credential value or stored component, file contents, the inherited environment, write payloads, the vault key, anything about Hidden credentials, and the Mac's display name.
- The sealing time is the inner message's sent time; the payload has no second copy of it.

**Request digest** (32 bytes): SHA-256 over the approval request's inner message, its exact bytes, signature included (`InnerMessage.digest`). It covers the sender, the recipient, the times, the binding digest, the deadline, the offers, the display and the response ID. ECDSA signatures are randomized, so every sealing has its own digest.

**Approval decision (kind 11)**, a fixed layout of 122 bytes, the same for every code:

| Field | Bytes |
|---|---|
| Pairing ID | 16 |
| Layout version | 1 |
| Request digest | 32 |
| Decision code | 1 |
| Duration ceiling | 8 |
| Approval-signature slot | 64 |

- **Decision codes:** 0 Deny, 1 Allow Once, 2 timed allowance for this credential; every other value is reserved and malformed. The duration ceiling is 0 for codes 0 and 1 and the offered timed duration for code 2; a code 2 with 0 is malformed.
- **Decision statement**, which the approval key signs for codes 1 and 2: `AskKey approval decision v1` ‖ approver's device ID (16) ‖ requester's device ID (16) ‖ pairing ID (16) ‖ request digest (32) ‖ decision code (1) ‖ duration ceiling (8). The approver is the inner message's sender and the requester its recipient; the Mac rebuilds the statement from the signed fields, never from plaintext routing data. Naming the requester makes a signature given to one Mac mean nothing to another.
- The slot holds the raw 64-byte ECDSA signature for codes 1 and 2 and 64 zero bytes for code 0. A Deny with any non-zero slot byte and an Allow whose signature does not verify are refused. Allow and Deny therefore have the same ciphertext length; the record's timing can still differ.
- The message ID of a decision is the request's response ID.

**Approval closed (kind 12)**, 59 bytes: pairing ID (16) ‖ layout version (1) ‖ request digest (32) ‖ outcome (1) ‖ applied code (1) ‖ applied duration (8). Its message ID is random.

| Outcome | Meaning |
|---|---|
| 1 | Applied: this approver's decision moved the request out of pending. The applied code is the decision code, and the applied duration, for code 2, is the number of seconds the Broker granted (the shortest of the signed ceiling, the current setting and the credential's deadline, rounded down); 0 otherwise. |
| 2 | Decided on the Mac. |
| 3 | Decided on another approver. |
| 4 | Expired. |
| 5 | Cancelled: the agent cancelled, the credential changed, agent access was paused, or this approver was turned off or removed. |
| 6 | Not applied: the Mac verified the decision but could not apply it as signed. A replacement request follows if the request is still pending. |

For outcomes 2–6 the applied code and duration are 0. Other outcomes are malformed.

**Approval receipt (kind 13)**, 49 bytes: pairing ID (16) ‖ layout version (1) ‖ request digest (32). Its message ID, the **receipt ID**, is the first 16 bytes of SHA-256 over `AskKey approval receipt id v1` and the response ID (16).

**Approver confirmation (kind 14)**, 113 bytes: pairing ID (16) ‖ layout version (1) ‖ code proof (32) ‖ approval-key signature (64) over the confirmation statement. Its message ID is random.

- **Confirmation statement:** `AskKey approver confirmation v1` ‖ iPhone's device ID (16) ‖ Mac's device ID (16) ‖ pairing ID (16) ‖ code proof (32).
- **Code proof:** HMAC-SHA256 over the Mac's device ID (16) ‖ the iPhone's device ID (16) ‖ the pairing ID (16), keyed with HKDF-SHA256 whose input key material is the six ASCII digits of the code (leading zeros kept, no space), salt the pairing ID (16 raw bytes), info `AskKey approver code v1`, output 32 bytes. The Mac compares the received proof in constant time with its own.

### Clocks and expiry

- Transport expiry and the authoritative deadline are separate. ADR 0013's checks (expiry against the receiver's clock, a lifetime of at most 10 minutes for these kinds, a sent time at most 5 minutes in the future) only decide whether a message is fresh enough to process; they tolerate clocks up to 5 minutes apart. **Only the Mac's clock decides whether a request is still pending**; a decision that arrives after the Broker request left pending changes nothing.
- The iPhone counts down from the moment it first verified a request, for the request deadline minus the inner message's sent time (both Mac-clock values, at most 300 seconds), so its own clock's offset cancels. The app stores the countdown's end on its own clock with the request when it first verifies it; re-opening the stored envelope, after a restart or otherwise, never starts the countdown again, and a request past its stored end is expired. The countdown does not subtract the delivery delay and can therefore show more time than the Mac has left; the Mac's closed message ends the card when the request expires. #310 and #314 test phones 2 and 4 minutes fast and slow.

### Sending and the return path

- **Seal once.** The Mac seals each request once per approver, records its request digest and its sealed envelope in the outstanding entry, and resends only those exact bytes; the iPhone does the same for its decision. Re-sealing would change the sent time and the signature, and with them the digest.
- **Known record names.** A record's name is its message ID (ADR 0013). The Mac knows the names of the decision (the response ID) and the receipt (the receipt ID) in advance. The response ID travels only inside the encrypted request, so until the iPhone's first save nobody else knows it or can create a record under it; an existing record under that name can then only be the iPhone's own bytes, which is why a send that finds the record already there counts as sent (`serverRecordChanged`, as the CloudKit transport already does). After the first save the name is ordinary routing data: anyone who can write to the account can delete the record and create another under it, which the Mac refuses and deletes. That costs availability, as deleting it would. A receipt send that finds its record already there also counts as sent, because the extension and the app may both send one; but the receipt ID is public once the decision is saved, so such a record may be junk, which the Mac refuses and deletes, and "Delivered" may then not show. Receipts only feed that display.
- **Polling the known records.** While at least one remote request is outstanding, the Mac fetches, by name, the decision record of every outstanding request and the receipt record of every request whose receipt has not arrived: every second while any outstanding request was sealed less than 60 seconds ago, otherwise every 3 seconds, until each request is decided, closed or expires. A fetch asks for at most 100 records per CloudKit call, uses the user-initiated quality of service, handles partial results per record, and waits as long as CloudKit's retry-after asks. A missing record means "not yet". A missing inbox zone is created again with its subscriptions and logged, as the zone-change poll does. A push hint, a wake and a screen unlock trigger an immediate fetch. The inbox's zone-change poll keeps its stage 2 schedule, and also runs about once a second while an approver confirmation sheet is open, because a confirmation has a random message ID and can only arrive through it.
- A record found by name goes through the same message handling as one found by the zone-change poll, without moving the change token. Both paths go through the messenger's serialized handling, which reserves a message ID before any suspension, so a message seen by both takes effect once and a duplicate confirmation counts once.
- **Retries.** The Mac retries a failed send of a request with the same bytes every 2 seconds, or after CloudKit's retry-after, until the deadline. The iPhone retries a failed decision send, "recipient unreachable" included, the same way until its countdown ends. Closed messages, receipts and confirmations are retried the same way until their own transport expiry. After a save that succeeded or found the record already there, the iPhone sends the same bytes again only if 30 seconds pass without a closed message, and then at most every 30 seconds while its countdown runs, so a deleted record comes back.

### Verifying and applying a decision

- The Mac applies a decision only if all of these hold; otherwise it refuses it without effect, deletes it, and leaves the outstanding entry as it was:
  1. ADR 0013's refusal rules pass: sender on the list, message-key signature, recipient, routing fields, times, record type and replay;
  2. an outstanding remote request exists for that sender whose response ID equals the message ID, and it is neither decided nor closed;
  3. the pairing ID matches the sender's current entry;
  4. the request digest matches the one the Mac recorded when it sealed that request;
  5. the code was offered in that request, and for code 2 the ceiling equals the offered duration;
  6. for codes 1 and 2 the approval-key signature verifies over the decision statement with the approval key in the sender's card on the Mac's list; for code 0 the slot is all zeros.

  **`AskKeyDevices` checks 1, 3 and 6**; **the App's handler checks 2, 4 and 5** against its outstanding entry. A decision that passes all six consumes the outstanding entry, whatever the Broker then does.
- **Other kinds.** The Mac accepts a receipt only if its message ID is the receipt ID of an outstanding request for that sender and its request digest matches; a receipt only marks the request delivered. The iPhone accepts a closed message only from the request's sender, with that request's pairing ID and digest, and stores one that arrives first as a terminal marker. A confirmation is checked as described under Approvers: `AskKeyDevices` verifies the pairing ID and the approval-key signature, and the App compares the code proof.
- **Vault entry.** The App applies the decision through a Vault entry. For codes 1 and 2 it re-reads the paired-device list and requires the sender's entry (device ID and pairing ID) to carry the approval flag, then runs the same revalidation as a local decision. For code 0 it does neither, because a local Deny never waits for policy I/O either; the Broker's active-approver check still applies. A missing flag, or an approver not in the set with the recorded generation, ends that approver's outstanding requests with outcome 5; any other refusal by the Vault entry or the Broker while the request is still pending is outcome 6.
- **Broker remote path** (`package` access). It takes the Broker request ID and capability from the outstanding entry, the captured operation request (matched as for consumption), the approver's pairing ID, the code and the ceiling. Inside the single locked transition from pending it checks, for every code, Deny included, that the pairing ID is in the active-approver set; it accepts only read requests and only codes 0–2; it maps code 0 only to the deny transition, code 1 to an approval for once, and code 2 to a single-credential timed allowance, never a group one, which it refuses while timed allowances are off or End Timed Allow on Lock is on, and otherwise grants under every rule of ADR 0002 for the shorter of the ceiling and the current setting. It treats the verified approval-key signature as the authentication a local read approval would ask for and never calls the local authentication. It reports whether this call moved the request out of pending and, for code 2, the duration granted.
- **First decision wins.** Every decision, local or remote, goes through the Broker's single transition from pending under its lock; any later one finds the request no longer pending. If a local decision's system authentication is still open when a remote decision wins, the existing cancellation ends it, and the local path ends with a distinct "decided elsewhere" result instead of an error.
- **Closed messages.** After a request leaves pending, the Mac sends every approver that still has it open an approval-closed message: outcome 1 only to the approver whose own call moved the request, outcome 3 to the others, and outcome 2, 4 or 5 when the Mac's prompt, the expiry or a cancellation ended it. A decision that verified but did not move the request gets the outcome that actually ended it. The iPhone shows its own decision's outcome only after the closed message arrives.
- **Outcome 6.** If a verified decision cannot be applied as signed, for example because timed allowances were turned off or End Timed Allow on Lock was turned on after the request was sealed, the Mac applies nothing, sends that approver outcome 6 and, if the request is still pending, a replacement request with the current offers, a new response ID and the original deadline. It never turns a decision into a different one.
- **Access records** of reads approved remotely, including reads under a timed allowance granted remotely, name the approving device as the Mac called it then; remote denials name it too. The name is an optional field inside the encrypted access record, so older records decode and there is no schema change.

### Revocation, removal and account changes

- Turning an iPhone's approval off, removing it on the Mac, an unpair notice from it, resetting the Mac's identity, and local erase remove it from the Broker's active-approver set first, then write storage, stop sending to it and close its outstanding requests. A later decision from it, Deny included, is refused. The Mac sends approval-closed with outcome 5 where it still can, sealing with the card it held before the removal. `AskKeyDevices` calls a hook the App provides before it commits any removal, including one caused by an unpair notice, so the set is updated first.
- An iCloud account change, sign-out or restriction on the Mac also empties the set first and closes every outstanding request; nothing is sent while the account is unavailable, and the Mac's prompt keeps working. The flags in the list do not change, because trust rests on the keys and the list, not on the account; when the device services are ready again, the set is loaded from the list.
- Removing a Mac on the iPhone, an unpair notice from it, or Stop Approving for This Mac drops that Mac's pending requests, stored decisions and their notifications on the iPhone.
- Pairing the same two devices again creates new entries with approval off on both sides. Replacing an entry is a revocation of the old pairing ID: it leaves the set and its outstanding requests close before the new entry is written.
- Revoking an approver stops its future decisions; timed allowances it granted earlier stay until they end or the person revokes them on the Mac, like any other allowance.
- An account change or sign-out on the iPhone stops remote approval there; the iPhone keeps its paired list and flags, as today, but drops stored requests, decisions and markers.
- Pausing agent access cancels pending requests as today; approvers get outcome 5.

### Replay and restarts

ADR 0013 left this to stage 4. A decision applies only to an outstanding remote request held in the memory of the App process that sealed it, and the first verified decision consumes that entry. A decision re-inserted after a restart finds no entry; one re-inserted before it finds the entry consumed. Neither device needs persistent processed-message IDs for decisions. The iPhone's stored requests and markers only keep a re-inserted request from being shown twice, and the launch-time rule below keeps a request from an earlier App process from being shown after one from a later process.

### Notification Service Extension

- `com.sudohg.askkey.ios.notification-service` runs for every push from the iPhone's `AlertMessage` subscription, which already has mutable content (ADR 0013). It first replaces the content with its own generic text: title and body from its own `push.message.title` and `push.message.body` strings, no subtitle, no attachments, category `askkey.message`, and only the record name in the user info. A push from an attacker's subscription that reaches the extension therefore never keeps its text.
- It then fetches the one record the push names, from the iPhone's own inbox only, and verifies it with a stateless verifier from `AskKeyDevices` that applies every refusal rule except replay and changes nothing, using the message and key-agreement keys and the paired-device list from the shared keychain access group.
- **Details only after verification.** Only for an approval request that verifies and comes from a Mac whose entry carries the iPhone's approval flag does the notification show the request: title `push.message.title` ("Ask Key"), body in the card's sentence, for example: “Codex” on “MacBook Pro” wants to use “GitHub Token” to run deploy.sh. The four parts are the requester's name (or "Local Agent"), the iPhone's own name for the Mac, the credential's name and the executable name, each from the decrypted record, never from the push. Each part is cleaned with ADR 0013's display-name rule, has the quotation marks U+201C and U+201D replaced with U+0022 so it cannot close the sentence's quotes, and, if longer than its limit in characters (extended grapheme clusters), shortened in the middle with `…` to that limit, keeping ⌈(limit − 1) / 2⌉ characters before it and the rest after: requester 24, Mac 24, credential 32, executable 32. The notification never contains a credential value, arguments, the working directory or variable names. Its thread identifier is `mac_<Mac's device ID>`.
- **Time-sensitive budget.** A detailed notification is time-sensitive if no time-sensitive notification from the same Mac was delivered in the preceding 120 seconds on the iPhone's clock; otherwise it uses the active level. The extension keeps the per-Mac times, and its delivery records without content, in its own keychain item: service `com.sudohg.askkey.ios.devices`, account `notification-service-state`, in the shared access group, accessible after first unlock, this device only. The targets carry the entitlement that time-sensitive notifications need.
- After showing a detailed notification it sends the approval receipt. For a delivery check it replies with the message key, as ADR 0013 planned; the app may reply again when it opens, and the Mac refuses the second reply as already answered.
- A push for another device's zone, a record that does not verify, a request from a Mac without the iPhone's approval flag, a fetch that fails or times out, or a phone not unlocked since it started leave the generic text, and the extension sends nothing.
- The extension never deletes an inbox record, never writes the paired-device list or the app's request store, never uses the approval key, and offers no notification actions; tapping only opens the app. Ask Key still never asks the person to act on a notification's text, category or action. Pushes from an attacker's subscription without mutable content never reach the extension and keep their text (ADR 0013); because real notifications now carry the card sentence, such a fake can look like a real request, so the rule that only the app's verified card can lead to a decision matters more, not less. A request re-inserted within its transport expiry can produce a second detailed notification, because the extension does not check replay; the app does not show it twice.
- **Where the details end up.** iOS shows notification content on the lock screen according to the person's Show Previews setting (default When Unlocked, so a locked phone shows only the title and generic text), and keeps delivered notifications, details included, in Notification Center until they are removed. The app removes the notifications of settled requests whenever it runs, matching them by the record name in the user info; the extension cannot.
- **Nothing depends on the extension for correctness.** The app fetches, verifies and sends the receipt itself when it processes a request. Whether a Secure Enclave key with ADR 0013's protection works in the extension on a locked phone is checked in #316, right after #315. If it does not, every notification stays generic and the receipt comes from the app (the **degraded mode**); the maintainer then decides between the degraded mode and blocking the stage before #319. This replaces ADR 0013's fallback of resetting identities and pairing again for this case.

### iPhone app

- The app becomes the approver. Its home screen shows pending requests when there are any, then the paired Macs and pairing as before.
- **Finding requests.** A request becomes pending when the app verifies it, from the record a push named or from its inbox poll, and only if the sending Mac's entry carries the iPhone's approval flag. While the app is in front it polls its inbox every 10 seconds, every 2 seconds while the Requests screen shows a pending or sent request, and on pull to refresh.
- **Card** (v0.2 style): one sentence with a subject, “Codex” on “MacBook Pro” wants to use “GitHub Token”, and one subtitle line, the command summary (middle-truncated at 160 characters as on the Mac); everything else under Details: the full command, the working directory, the delivered names, the requester and purpose marked not verified, the time left and the Mac's paired date. Fields marked shortened say so. The fields arrive preformatted (see Encodings); the app shows them as plain text (no links, no data detectors) without quoting or escaping them again, wraps long names as the Mac card does, and names the Mac by its own name for it; the request carries no Mac name.
- **Buttons:** Deny, Allow Once, and the timed allowance when offered ("Allow for 30 Minutes"). Allow signs the decision statement with the approval key, which asks for Face ID or Touch ID with a new authentication context each time and no passcode button (ADR 0013); a cancelled or failed prompt sends nothing and the person can try again while time is left. Deny sends at once without Face ID. The app checks the time left, the iCloud account and the identity before sending, and for Allow again after the prompt.
- **One decision per request.** Once a decision is built, the app stores its sealed envelope before the first send, disables the other buttons, and sends only those bytes (see Retries). After sending, the card says it is waiting for the Mac, then shows the closed outcome, using the code and duration the Mac reports for outcome 1. Without a closed message by the end of the countdown it says to check the Mac.
- **Durable state.** Each request moves through received → decision stored → sent → closed or expired. The app stores the request's sealed envelope (ciphertext only) before it reports the message processed, so the inbox copy is deleted only after the local copy exists, and opens a stored envelope again with the stateless verifier. It keeps stored decisions and terminal markers, including closed messages that arrived before their request (keyed by sender, pairing ID and request digest), until the request's or marker's transport expiry. It never stores opened content. The store lives in the app's own container, protected until first unlock; the extension never reads or writes it. An app restart resumes waiting or resending. An account change or identity reset drops every stored request, decision and marker.
- **Mac restarts.** The app keeps, per Mac, the latest launch time among its stored requests. A verified request with a later launch time marks that Mac's older cards gone, because their outstanding entries died with the old process; a request with an earlier launch time than that is refused. Equal launch times displace nothing.
- **Limits.** At most 16 pending requests per Mac and 64 in all; further requests are refused. A closed message is accepted only from the request's own sender and only from a Mac whose entry carries the approval flag; at most 16 terminal markers per Mac and 64 in all are kept, and further closed messages that match no stored request are refused.
- **Privacy.** The app covers its window when it moves to the background, and when it becomes inactive while no Face ID prompt is running, so app-switcher snapshots show no request. Anyone holding the unlocked phone can read a pending card and its Details, as anyone at an unlocked Mac can read its prompt, and can deny it; allowing needs Face ID.
- **Mac names.** The person can rename a Mac on the iPhone. The iPhone keeps its Mac names unique: a newly paired Mac whose proposed name matches an existing one gets a numbered name and a prompt to rename.
- **Approver confirmation:** a Mac's detail in Paired Macs always offers **Approve Requests from This Mac**, which sends a new confirmation even while the flag is set (for example after a wrong code or when the Mac asks again), and, once the flag is set, **Stop Approving for This Mac** (see Approvers).
- A request with an unknown layout version is refused; the Mac's prompt still works and the request expires.

### Macs on the iPhone's list are not trusted for anything else

A forged QR code can put a fake Mac on the iPhone's list (ADR 0013). The iPhone accepts approval requests only from Macs for which the person completed the approver confirmation on the iPhone, typing a code they should only take from that Mac's own screen; a fake Mac the person never confirmed cannot send requests or produce detailed notifications. A decision is bound to the requester's device ID and the request digest, and the real Mac applies only decisions for requests it sent, from devices it made approvers, so a decision the iPhone gives a fake Mac is useless against the real one. Each Mac's requests count against its own limit and its own time-sensitive budget. The iPhone acts on a request only by signing a decision for its sender and holds no credential. Any listed Mac learns from delivery-check replies when the phone is on and reachable, and a confirmed Mac also learns it from receipts. Authority over credentials comes only from the requesting Mac's own list and approver flags, behind the Mac's system authentication and the in-hand code.

On macOS 26 a grouped list holding a single row with a control can ignore clicks (#299, #300): the control must not sit in a one-row grouped list, and a required desktop flow clicks it with exactly one paired device on the macOS 26 runner.

### Code layout

- `AskKeyDevices` gains kinds 10–14 with their payloads, statements and refusal rules, the approval flag and list serialization version 2, a caller-supplied handler for verified approval messages, the removal hook, a named-fetch capability as a separate protocol that the CloudKit and in-memory transports adopt (so other `DeviceTransport` conformers keep compiling), and the stateless verifier. It still has no local dependency.
- `AskKeyBroker` gains the remote decision path and the active-approver set (`package` access); `AskKeyVault` the approval flag's write rule, the remote decision entry with revalidation and the access record field; `AskKeyAppKit` the remote approval coordinator and the interface. The module edges do not change; `AskKeyBroker` and `AskKeyHelper` still do not depend on `AskKeyDevices`.
- `iOS/` gains the extension target and the approver screens. The extension links `AskKeyDevices` and the keychain code, not the app's views.

### Out of scope

Writes, organize operations and group timed allowances from the iPhone; approving several requests with one Face ID; revoking timed allowances or reading access records on the iPhone; notification actions of any kind; Mac-to-Mac approval and a Mac approver (stage 3, which reuses these kinds after its own push investigation and must gate a Mac's remote decision in the App, because the Mac approval key has no per-use authentication); a per-credential approver setting; the notification filtering entitlement; opening pairing from the Camera or WeChat; payload version negotiation; persisting outstanding remote requests across Mac restarts; changes to record types, fields, zones, subscriptions or the 16 KiB payload cap; the App Store submission, Apple Watch and iPad.

### Resolutions of #308

- The request's sealing time is the inner message's signed sent time; #308 listed it as a payload field, which would only have duplicated it.
- #308 left the payload layouts, caps, shortening, labels and test-vector inputs to this ADR; they are fixed above. The display fields take at most 12,825 bytes, the "about 12 KiB" #308 budgeted, and the whole payload at most 12,917.
- Every kind 10–14 payload carries a layout version after the pairing ID, not only the request, so all five can change the same way.
- The offers are a bitmask over the decision codes, so verification step 5 is a bit test.
- End Timed Allow on Lock: the Broker today permits a timed grant while the screen is unlocked even when the setting is on; decision 1 forbids remote timed grants whenever it is on, so the remote path refuses code 2 on the setting alone, not on the lock state.
- The remote Deny skips the Vault's policy revalidation and the flag re-read, as a local Deny does; the Broker's active-approver check is what refuses a revoked approver's Deny.
- An account change on the Mac suspends approvers instead of clearing their flags; #308 listed it with the revocation paths without saying whether authority returns.
- The active-approver set carries an enablement generation per approver and a revocation counter, so a reload or a new enablement can neither undo a revocation that raced with it nor revive a decision for a request sealed under an earlier enablement; #308 described the set as bare pairing IDs.
- Requester, purpose and credential name are escaped on the Mac like the other fields, and the iPhone refuses control and line-break characters instead of applying ADR 0008's escaping a second time; #308 said only that the iPhone applies the rules again.
- #308 says the encrypted display exists in CloudKit and on the iPhone only until the request's transport expiry. Expiry is checked on the receiver's clock and deletion happens at the recipient's next poll, so this ADR states the actual retention under Consequences.
- Early closed messages are kept only from Macs with the approval flag and within a per-Mac and overall limit; #308 set no limit.
- A request from an earlier Mac launch than one already stored is refused; #308 said only that an older launch time never displaces a newer card.
- A matching confirmation from a device other than the selected one ends the attempt instead of only being refused, because that device now knows the code.
- The receipt's message ID is derived and the decision's is chosen by the Mac, where ADR 0013 says message IDs are 16 random bytes; the response ID is still random.

## Consequences

The person can decide an agent's read request on their iPhone while away from the Mac, through the identity, list, zones, record types and subscriptions of stage 2, with no change to the Broker protocol. Every Allow needs the enrolled face or finger on the phone and a signature the Mac verifies against a key it learned at pairing, bound to the exact request the Mac sealed; a Deny needs neither but can only deny.

Accepted side effects:

- With End Timed Allow on Lock off, its default, a timed allowance can start from the iPhone while the Mac is locked and nobody is at it, and any program running as the local user can use that credential until it ends.
- Someone holding the person's unlocked phone can deny pending requests, read their cards, stop approving and remove Macs. That costs availability only; nobody can allow without the enrolled face or finger.
- With Show Previews set to Always, the requester, Mac, credential and program names appear on the locked phone, which the Mac's own prompt never shows while locked; with any setting they stay in Notification Center until the app removes them.

What leaves the Mac in a request is the display listed above together with the binding digest, the deadline, the App's launch time and the offers with the timed duration, from which an approver can infer whether timed allowances are on and whether End Timed Allow on Lock is off; all of it is encrypted to each approver. CloudKit holds it as ciphertext until the iPhone processes it, or deletes it at a later poll once it has expired; a phone that never comes back leaves it there. The iPhone keeps the ciphertext until the request's transport expiry on its own clock, deleted the next time the app runs after that, so with a slow clock or a suspended app it can outlive the 10-minute lifetime. Apple, as the operator of iCloud and the push service, sees which devices exchange messages and when, including the timing that can distinguish a quick Deny from an Allow after Face ID, but no content.

Residual risks:

- Anyone who can write to the account can still show any notification under Ask Key's name (ADR 0013), now one that can look like a real request; the only path to a decision is the app's verified card.
- A local agent can make the phone show up to 16 outstanding requests per Mac at a time; only the first notification per Mac in two minutes is time-sensitive.
- If the person types the approver code on the iPhone under a fake Mac's entry, the fake Mac can recover the six digits from the code proof by trying every code. It gains nothing from them unless the person also selected, on the real Mac, a device that the same attacker paired through the residual pairing attack (ADR 0013); both screens name the device they act on to stand against that.
- The iPhone's countdown can show more time than the Mac has left after a slow delivery; the Mac decides, and its closed message corrects the card.
- A version 2 paired-device list is refused by stage 2 builds. Stage 2 shipped only in the maintainer's Local builds and Ad Hoc iPhone builds, so a downgrade affects only those; the person resets and pairs again.

The statements, bindings, the Broker remote path, the active-approver set, the approval flag's write rule, the approver confirmation and the extension are `risk:security` and are reviewed line by line. CI tests the round trip, the races and every refusal with software keys, an in-memory transport and fake device services; the Secure Enclave, CloudKit, push, the extension on a locked phone, App Nap, latency and TestFlight are verified only on real devices, in #316 and #319.
