# ADR 0011: In-app updates with Sparkle 2

## Status

Accepted. Supersedes the updater sentences in [ADR 0006](0006-release-process.md) ("There is no updater" and "Sparkle or any in-app updater … need their own issue") and the updater part of the release sentence in [ADR 0005](0005-distribution-and-client-integration.md). [#257](https://github.com/sudoHG/AskKey/issues/257) adds the App side and the packaging; [#258](https://github.com/sudoHG/AskKey/issues/258) adds the public signing key; [#259](https://github.com/sudoHG/AskKey/issues/259) publishes the signed appcast and the website redirect.

## Context

Users install Ask Key by replacing `/Applications/Ask Key.app` with the app from a notarized DMG on GitHub Releases. Most never learn that a new version exists. Releases stay signed and notarized on the maintainer's Mac and each publication needs the maintainer's approval ([ADR 0006](0006-release-process.md)); an updater must not weaken that, must not install anything without the user, and must not interrupt requests an agent is waiting on.

## Decision

1. **Dependency.** Sparkle 2 through SwiftPM, pinned with `exact: "2.10.1"` (signed feeds need 2.9 or later). Only the production `AskKeyApp` executable depends on it, in [SparkleSoftwareUpdater](../../Sources/AskKeyApp/SparkleSoftwareUpdater.swift). `AskKeyAppKit` defines the [updater interface](../../Sources/AskKeyAppKit/SoftwareUpdate/SoftwareUpdater.swift) and the pure policy types, so `swift test`, the E2E app and the `askkey` helper never link Sparkle. Sparkle's command-line tools come only from the resolved SwiftPM artifact.
2. **Feed.** `SUFeedURL` is `https://askkey.sudohg.com/appcast.xml`, on the maintainer's own domain. The website answers it with a temporary (302) redirect to `https://github.com/sudoHG/AskKey/releases/latest/download/appcast.xml` (#259). The feed is therefore a GitHub Release asset: it goes live when a release is published, which already needs the maintainer's approval, and releases need no website deploy. Every installed copy keeps requesting the URL on our domain, so it is a product identifier ([AGENTS.md](../../AGENTS.md)). Because the domain is ours, a later change can serve the feed directly or from a mirror for users in mainland China without a new release. Enclosures use versioned GitHub Release URLs (`https://github.com/sudoHG/AskKey/releases/download/v<version>/AskKey-<version>.dmg`), and a later appcast can point them elsewhere. Feeds and archives must be EdDSA-signed, so neither host is trusted for integrity: `SURequireSignedFeed` and `SUVerifyUpdateBeforeExtraction` are `YES`, and `SUSignedFeedFailureExpirationInterval` is `0`: otherwise Sparkle 2.10.1 accepts a feed that fails validation once 20 days have passed since the first failure (`SUAppcastDriver.m:136-152`), and a zero interval disables that recovery. `SUPublicEDKey` comes from the committed file `scripts/sparkle-public-key.txt` (#258). `Release` builds fail unless that file holds one base64-encoded 32-byte key, so no release ships an updater without a key.
3. **No silent installs.** `SUAllowsAutomaticUpdates` and `SUAutomaticallyUpdate` are `NO`, so every install needs the user's click. `SUEnableAutomaticChecks` stays unset, so Sparkle asks on the second launch whether to check automatically; **Check for Updates Automatically** in Settings → General changes it later. `SUEnableSystemProfiling` is `NO`. The check interval stays at Sparkle's default of one day. Because Ask Key runs in the background, the adapter also implements Sparkle's gentle reminders: a scheduled check's alert still appears without taking focus, and when notifications are already authorized or provisional (Ask Key never asks) one local notification names the version; clicking it brings the alert forward without opening the management window, and it is removed once the user attends to the update or the session ends ([SoftwareUpdateReminder](../../Sources/AskKeyAppKit/SoftwareUpdate/SoftwareUpdateReminder.swift)).
4. **Where it runs.** [SoftwareUpdateAvailability](../../Sources/AskKeyAppKit/SoftwareUpdate/SoftwareUpdateAvailability.swift) creates an updater only when all of these hold: the Info.plist's `SUFeedURL` is exactly the feed above, which only `Release` mode writes; the bundle ID is `com.sudohg.askkey.app`; none of `AskKeyLocalTesting`, `AskKeyE2ETesting` or `AskKeyRequiresDebugRunDirectory` is present, whatever its value (the check rejects every `AskKey`-prefixed Info.plist key, which only those testing modes write, so the release binary never names the E2E flag); and [OfficialInstallTopology](../../Sources/AskKeyBroker/OfficialInstallTopology.swift) accepts the official, non-development runtime at `/Applications/Ask Key.app`. Otherwise no Sparkle object exists and no update controls are shown. The production executable passes the factory through `AppRuntimeConfiguration`; the E2E app passes none.
5. **Relaunch only when idle.** `updater(_:shouldPostponeRelaunchForUpdate:untilInvokingBlock:)` asks [SoftwareUpdateRelaunchGate](../../Sources/AskKeyAppKit/SoftwareUpdate/SoftwareUpdateRelaunchPolicy.swift). The relaunch waits while any of these is true: an approval prompt is waiting for a decision; an approved request has not been used yet (a relaunch would lose the approval); a Broker call is running, which covers runs with their temporary deliveries and every text, file or organization write call; a file or component upload is open between the agent's calls (until it is frozen, cancelled or untouched for the Broker's five-minute upload lifetime); or a system authentication prompt is showing. While it waits, the gate checks again every second, so requests that arrive meanwhile keep it waiting, and it continues the relaunch exactly once when all are clear. An update never cancels, denies or orphans a request. A request that starts in the moment between the last check and termination ends as it would when the user quits Ask Key. Timed allowances do not postpone the relaunch, because they can last hours. Instead Settings states what a relaunch ends, matching current behaviour: management locks again because its session lives only in memory, timed allowances end because the running Broker holds them in memory, and the replay receipts of completed operations last only for that App runtime, as after any restart. Permissions, credentials and Agent access settings are kept.
6. **Running agents.** The install path, helper path and Broker protocol version stay unchanged, so client configurations need no change, and helper processes that are already running keep working against the new Broker (helper trust compares Team IDs, see [HelperCodeSignatureTrust](../../Sources/AskKeyIntegrations/HelperCodeSignatureTrust.swift)). Tools added in a new version appear only after the agent restarts its MCP server.
7. **Downgrades and migrations.** Sparkle only offers newer versions, and pulling a bad update means shipping a fixed, higher version. If automatic installs are ever enabled, every release that adds a library migration must set `sparkle:minimumAutoupdateVersion` to its own version.
8. **Network and privacy.** The update check is Ask Key's only outbound network request. A check sends `GET https://askkey.sudohg.com/appcast.xml` with no query parameters: system profiling is off and no feed parameters are added (`SPUUpdater.m:1249-1277` in Sparkle 2.10.1). It goes through Cloudflare and follows the redirect to GitHub; an update download goes to GitHub. Both see the IP address. The request headers are:
   - `User-Agent: Ask Key/<CFBundleShortVersionString> Sparkle/2.10.1`. Sparkle builds the same format from the localized display name and drops non-ASCII characters (`SPUUserAgent+Private.m:22-23`, `SUHost.m:121-133`), which would send `??` in the Chinese interface, so the adapter sets `userAgentString` with the fixed English name; Sparkle applies it to every request (`SPUUpdater.m:921`, `SPUDownloadDriver.m:131-133`).
   - `Accept: application/rss+xml,*/*;q=0.1` on the appcast request only (`SUAppcastDriver.m:74`).
   - The headers macOS URL loading adds to any request, such as `Host`, `Accept-Language` (from the preferred languages) and `Accept-Encoding`. Sparkle uses the default session configuration (`SPUDownloader.m:84`), so cookies a host sets are stored for Ask Key and returned to that host. The appcast and release notes bypass the local cache (`SPUDownloadDriver.m:129`).
   The archive download sends the same `User-Agent` without `Accept` (`SPUCoreBasedUpdateDriver.m:130`). If an appcast item links its release notes with `sparkle:releaseNotesLink`, showing them fetches that URL with the same headers; #259 decides the appcast contents.
9. **Known limitation.** Sparkle's standard windows follow the macOS language, not Ask Key's in-app language setting. This is accepted for now.

**Packaging.** `scripts/build-app.sh` embeds `Sparkle.framework` in `Contents/Frameworks` in every mode, so the binary always launches, and removes its `XPCServices`, which a non-sandboxed app does not need. It makes sure the executable's rpath includes `@executable_path/../Frameworks` and removes rpaths into the checkout or derived data, so dyld loads only the embedded framework and no local path ships. It signs nested code inside out with the existing options (Sparkle's `Autoupdate`, `Updater.app`, the framework, the helper and its resource bundle, then the app) without `--deep`, which is kept for verification. Only `Release` mode writes the Sparkle keys from decisions 2 and 3; Debug, `Local` and E2E bundles carry none. The app stays unsandboxed.

**Publication.** Every notarized release writes `appcast.xml` with [generate-appcast.py](../../scripts/generate-appcast.py) and publishes it as a Release asset ([ADR 0006](0006-release-process.md)); until a release carries it, the redirect target returns 404. The feed has one item. `sparkle:version` and `sparkle:shortVersionString` are the product version, which packaging requires to equal the app's `CFBundleVersion`; `sparkle:minimumSystemVersion` is `14.0.0`; the enclosure is the versioned DMG URL from decision 2 with its `length` and `sparkle:edSignature`; `--critical` adds an empty `sparkle:criticalUpdate`, which marks the update critical for every older version. The release notes are embedded in the signed feed as Markdown `description` elements in English and Simplified Chinese (`xml:lang` `en` and `zh-Hans`). Sparkle 2.10.1 picks the one that best matches the macOS preferred languages (`SUAppcast.m:237-276`) and renders Markdown in a text view, not a web view (`SUUpdateAlert.m:181-195`, `SUUpdateAlert.m:333-339`). There is no `sparkle:releaseNotesLink`, so showing the notes fetches nothing; `sparkle:fullReleaseNotesLink` names the GitHub Release and is only opened in the browser when the user clicks Version History (`SPUStandardUserDriver.m:679-685`). `sign_update` from the resolved SwiftPM artifact signs the DMG and then the feed with the key file that Ask Key delivers in `SPARKLE_ED_KEY_FILE` to one `askkey run --wait-for-approval` request, and verifies both before the feed is written. Because `sign_update --verify` derives the public key from the delivered private key, the generator also checks the DMG signature against `scripts/sparkle-public-key.txt` with CryptoKit, so a delivered key that does not match the app's `SUPublicEDKey` fails packaging and nothing is written. `sign_update` output, which can echo key material, is never shown, and no keychain item is created.

Sparkle follows the website's redirect to GitHub and GitHub's redirects to its asset host. The downloader runs in process because the Info.plist does not set `SUEnableDownloaderService` (`SPUDownloadDriver.m:58-60`, `SPUDownloadDriver.m:108-112`, `SPUXPCServiceInfo.m:16-22`) and uses a default `NSURLSession` whose delegate does not implement `URLSession:task:willPerformHTTPRedirection:newRequest:completionHandler:` (`SPUDownloader.m:27`, `SPUDownloader.m:83-86`; the method appears nowhere in Sparkle's `Downloader` or `Sparkle` sources), so `NSURLSession` follows redirects itself. Only the initial URL's scheme is checked (`SPUDownloader.m:65-81`), the status check sees the final response (`SPUDownloader.m:191-211`), and relative appcast URLs resolve against the final URL (`SPUDownloader.m:214-224`, `SUAppcastDriver.m:185`); the feed uses absolute URLs. No host is trusted for integrity: the feed and DMG signatures are.

## Consequences

Users of the official install learn about updates and install them with one confirmation, and releases still need only the maintainer's approval to publish. The appcast, its signing and the website redirect are release work in #259; until #258 lands, `Release` builds fail by design. Update checks add a network request that reveals the IP address, app version and preferred languages to Cloudflare and GitHub, as documented in the README and [SECURITY.md](../../SECURITY.md). A relaunch waits for as long as agent work continues.
