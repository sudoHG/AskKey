# ADR 0001: Credential domain, local storage and the v15 baseline

## Status

Accepted. Records the current product, replacing the obsolete upgrade portions of legacy ADR 0026.

## Context

AskKey needs a single authorization object and must open supported existing libraries without importing the old Project/Environment model. The legacy v15 schema is the compatibility baseline. [Issue #31](https://github.com/sudoHG/AskKey/issues/31), including its interrupted-creation rules and atomic-creation addendum, supersedes the old staged Lokalite upgrade design. The decisions below supersede #31 rule 6's pending-key resume: no existing pending value proves its origin, so exact first-creation contents are discarded and recreated without an App key.

## Decision

- A globally named credential contains text, file bytes or multiple components and has one Allow, Ask or Hidden permission; Ask is the default. Groups organize credentials and confer no authority. Display names are trimmed; uniqueness uses NFC and Unicode case folding. There is no folder association or current-directory inference.
- Store sensitive fields with authenticated encryption, authenticate each credential record together with its policy, and use a keyed normalized-name index. The App owns the vault key; the helper never opens the database or loads that key. Opening the library for agent service does not create an authenticated management session.
- `askkey-0001-baseline` preserves the v15 CREATE statements. Adoption accepts exactly the 14 ordered v15 migration identifiers with matching normalized schema and valid App-key authentication, then replaces only migration history in one transaction. Already normalized libraries are validated without repeating adoption.
- The current schema also includes `askkey-0002-drop-legacy-tables`: drop the five old domain tables only if they contain nothing beyond the `Default` seed; otherwise preserve every old table and row and still record the migration. Old tables retained for data preservation do not restore old product APIs.
- `askkey-0003-component-metadata` adds nullable `credentials.encrypted_component_metadata`. Its vault-key-encrypted JSON is `{version: 1, components: [{name, payloadKind, delivery}]}` in payload order, with no component values or filenames. A nil field is omitted from the authenticated JSON so existing v1 record tags remain valid; non-nil ciphertext is covered by the same record HMAC. Every new or changed mapping writes this metadata with its payload; unchanged mappings survive value-only writes and recycling/restoration.
- The exclusive reopening gate closes before opening/migrating the library. The first backfill runs inside the `askkey-0003` migration transaction: add the column, authenticate and project every credential (including Hidden and recycled rows), encrypt metadata, reseal rows, and record an authenticated library-level completion marker together. Text/file projections use only the stored kind and separate mapping without opening payloads or filenames; bundle decoding reads only names, value cases and delivery, ignoring material and its delivery-time filename/size validation. Payload ciphertext and timestamps stay unchanged. The v2 marker in `config.component_metadata_completion_v2` is canonical Base64 of an HMAC-SHA256 over `AskKey component metadata complete v2` followed by a NUL byte. Its 32-byte key is derived from the vault key with HKDF-SHA256, an empty salt and the separate authentication domain `AskKey component metadata completion authentication v2`. Even empty libraries run 0003 only with their App-held key; there is no marker-initialization exception for existing 0003 libraries.
- Failure/interruption rolls back the column, backfill, marker and third migration identifier, leaving a `0002` library openable by v0.3.2. The current App retains authenticated management access, including reveal, edits, creation, recycling/restoration and deletion; compatibility writes omit metadata and retain the historical authentication encoding. Projection decode/validation errors name affected credential display names only and ask the user to fix the credential or permanently delete it from the Recycle Bin, then reopen. Storage failures have a separate cause with disk/access checks and retry guidance, never advice to delete credentials. A completion marker already present in a 0002 library is an integrity error. Successful backfill is silent.
- Metadata failures have a distinct unavailable state in management, separate from a resumable policy pause. Resume is not offered and cannot mutate policy while metadata is unavailable; agents receive the existing `agent_access_paused` code with guidance to review and resolve the issue in the library, then reopen. No wire shape/version, saved policy or recovery latch changes. Named failure details appear only in an authenticated management session; otherwise the notice is generic. Unavailable approval mappings explicitly say that the run will be refused and suggest Deny.
- Once complete, opening verifies the completion marker and requires metadata on every row. A development-only v1 marker in `config.component_metadata_completion_v1` is accepted only when its vault-key AEAD decrypts to `AskKey component metadata complete v1` and every row has metadata; opening atomically inserts v2 and deletes v1 once. Missing, invalid or mixed-version markers, or replayed historical rows without metadata, raise a specific, actionable component-metadata integrity error, preserve management access and keep Agent access off. Opening never silently backfills or reseals such rows. Reopening an intact completed library is idempotent. The marker authenticates completion only, not other config values, and does not prevent whole-library rollback. Discovery and approval read only metadata; the App binds the complete ordered projection into read approval digests and checks decrypted components against that bound projection before delivery.
- New libraries finish at all three AskKey identifiers. **Downgrade:** v0.3.2 rejects the third migration identifier before opening or mutating the library, with “The library has an unsupported migration history. Existing data was not changed.” An upgraded library cannot be used directly by v0.3.2; there is no reverse migration. Compatibility tests preserve the v0.3.2 migration-history gate.
- With an App key, require its supported current database and never fall back to a pending key. Without an App key, never adopt an existing pending key, regardless of its value or access control. If this Vault still holds an open store for the same path, a missing App key fails closed before any discard or recreation. Otherwise, if the current database is absent without orphaned current sidecars, delete any pending item and create with a newly generated key. If a current database exists, require exactly first-creation contents at the baseline/0002 schema, or those same empty contents at 0003 with only one well-formed v1 or v2 completion marker added; then discard that database, its current sidecars and the pending item and create with a newly generated key. Without the key, marker validation is structural only: canonical Base64 of exactly 32 bytes for v2, or an AES-GCM combined value with the exact expected nonce/ciphertext/tag lengths for v1. Mixed versions, any credential, extra config row, malformed marker, unknown history or mismatched schema prevent discard. The pending item need not exist or hold a valid key. Pending deletion rejects duplicate or outside-keychain items before any library deletion or creation.
- Build first creation at `credentials-v2.db.creating` through 0002, checkpoint and close it, set `0600`, synchronize it and rename exclusively to `credentials-v2.db`. Synchronize the database and its directory chain, save the key generated in this process as pending, promote the generated bytes directly and delete that pending key. Then run the key-bound 0003 migration, including its authenticated completion marker, before adoption. Interruption before 0003 leaves a supported 0002 library. Pending is only an ordering marker and is checked against those bytes; a failed post-promotion check deletes the newly written App key before throwing. Creation cleanup owns only the `.creating` file and its sidecars; the first-creation discard rule additionally owns only the verified current database and its current sidecars. An existing pending value is never resumed.
- Successful opens tighten the directory to `0700` and the database to `0600`. Stale pending-key deletion is best effort; for an empty App-key library, a different or unreadable pending key is preserved. Historical databases, migration journals and `.pending*` siblings are not opening inputs and are never read, moved, rewritten or deleted by bootstrap.

These decisions follow legacy ADR 0026's domain, naming, encryption and folder-removal sections, #31, the legacy-table removal in [#33](https://github.com/sudoHG/AskKey/issues/33) and the directory durability follow-up in [#43](https://github.com/sudoHG/AskKey/issues/43). Current evidence is the [schema implementation](../../Sources/AskKeyVault/Storage/VaultStoreMigrations.swift), [bootstrap](../../Sources/AskKeyVault/Migration/VaultBootstrap.swift), [record authentication](../../Sources/AskKeyVault/Crypto/CredentialRecordAuthentication.swift) and [name index](../../Sources/AskKeyVault/Models/CredentialName.swift).

## Consequences

Supported libraries retain their credentials, permissions, ciphertext and receipts. Unsupported states require diagnosis rather than a guessed upgrade or a silently replaced key. A pending key proves no origin and never authorizes adoption. Without an App key, an exactly empty first-creation library is discarded and recreated, including 0003 when its only additional content is a well-formed completion marker, unless this Vault still holds its open store. Any credential or unknown content prevents discard. AskKey assumes the App is the sole library opener; file preflight is defense in depth, not protection against a hostile same-user process changing files concurrently.
